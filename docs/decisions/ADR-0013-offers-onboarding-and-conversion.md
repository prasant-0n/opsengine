# ADR-0013: Offers reuse the approval engine, offer money is integer cents, and candidate→employee conversion is governed and idempotent
**Date:** 2026-10-20
**Status:** Accepted (feature recruitment-onboarding)
**Context:** PRD Module 3 requires offer generation from approved templates, an approval chain, acceptance status, and transition to preboarding; Module 4 requires converting an accepted candidate into a preboarding employee **without duplicating identity/employee records**, configurable onboarding checklists, induction, and a governed probation extension/confirmation workflow. The PRD decision matrix (row "Candidate offer") requires that compensation/offer approval be an authorized human action distinct from the recruiter who prepared it, and Module 3 explicitly forbids AI from auto-rejecting (or, by extension, auto-deciding) candidates. A naive slice might (a) store offer compensation as `Float`, (b) build a bespoke offer approval chain parallel to the approved engine, or (c) create a duplicate `Employee` row on every conversion attempt / retry.
**Decision:**
1. **Offer money:** offer base/variable compensation is an integer number of cents stored as `BigInt` and serialized as a string in JSON, with an explicit 3-letter currency. Same rule as finance (ADR-0012). No `Float`/`Decimal`-as-float.
2. **Approvals reuse the engine:** an offer approval raises an `approval_instance` with `subjectType:"offer"` through the Feature #9 engine (ADR-0011). Sending an offer is a governed action that **requires the instance to be `approved` first**; within-threshold or bespoke chains are not built. Offer templates are validated data (name + body + terms), never tenant executable JS.
3. **Human-only decisions:** offer send/accept/decline/withdraw and every probation decision are authorized human actions recorded with actor + timestamp. AI may draft/summarise but must not send, accept, or reject — enforced at the API boundary (no AI path can call these endpoints).
4. **Conversion is governed and idempotent:** candidate→employee conversion is a dedicated audited POST requiring `onboarding.convert_employee`. The `Employee` is created **once** (de-duplicated by tenant + email within a transaction) and the candidate plan is linked to it; a repeated call returns the same employee rather than creating a duplicate identity record. The candidate record is retained (referenced), not deleted.
5. **Probation decisions are governed with separation of duties:** `onboarding.probation.decide` is a distinct permission from `onboarding.probation.review`; `confirm | extend | terminate` are validated data (no tenant JS), written to `StageHistory`; `terminate` does not itself trigger offboarding (deferred).
**Rationale:** Reusing the approval engine avoids a second, divergent approval authority and keeps offer + probation governance auditable in one place (consistent with ADR-0011/0012). Integer-cent money keeps hiring compensation free of rounding drift. Idempotent, governed conversion satisfies the Module 4 "without duplicating identity" rule under retries and concurrent requests.
**Consequences:** Offer PDF/e-signature, resume/document binary storage, notification/calendar delivery, and the Module 4 exit/offboarding tail remain deferred. Probation `terminate` is a decision record only in this slice. Verified by unit tests (offer status machine, completion/dependency derivation, conversion idempotency guard, money guards) and smoke/browser tests (governed send requires approval, governed PATCH 400, cross-tenant 404, convert-twice returns same employee).
