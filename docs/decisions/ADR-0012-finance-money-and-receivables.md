# ADR-0012: Finance money is integer cents, client receivables are tenant-scoped, and commercial exceptions reuse the approval engine
**Date:** 2026-10-20
**Status:** Accepted (feature finance)
**Context:** PRD Module 12 requires invoices, receivables, partial payments, append-only payment/adjustment history, and commercial approval for terms/credit/discount/write-off, while explicitly (a) forbidding binary floating-point for money (PRD Module 12 + §12), (b) separating a tenant's own client receivables from platform subscription billing which belongs to the control plane (PRD §5 Module 0A), (c) deferring statutory tax computation and GL posting to a later reviewed specification (PRD §2 Non-Goals + Module 12 last bullet), and (d) requiring that Finance validation and SBU Head business approval be separate actions where policy says so (PRD §4 decision matrix row "Invoice issue / receivable"). A naive slice might store money as `Float`/`Number`, mix platform and tenant billing, compute statutory tax, or build a second approval mechanism parallel to the just-approved approval engine.
**Decision:**
1. **Money:** every amount is an integer number of cents stored as `BigInt` and serialized as a string in JSON; currency is an explicit 3-letter code. Totals are derived with integer arithmetic only; no `Float`/`Decimal`-as-float is used anywhere. No FX conversion in this slice.
2. **Domain separation:** this slice implements only the tenant's client invoices/receivables. Platform subscription billing stays in the control plane (Module 0A) and its records, permissions, and APIs are never mixed with tenant finance rows.
3. **Payments are append-only:** a finalized payment is never edited; corrections are new `PaymentAdjustment` rows (`reversal | credit_note | discount | write_off`, signed). Receivable status/outstanding are derived, not hand-edited.
4. **Commercial exceptions reuse the approval engine:** terms/credit/discount/write-off beyond a threshold raise an `approval_instance` with `subjectType:"invoice"` through the Feature #9 engine (ADR-0011). The governed apply-step checks the instance is `approved` before the exception takes effect. Within-threshold adjustments require `finance.receivable.adjust`.
5. **Statutory tax & GL posting are out of scope:** `taxCents` is a stored figure, not a computed statutory tax; no ledger posting.
**Rationale:** Integer cents eliminate float rounding drift in money math and match the established `amountCents` convention. Explicit domain separation satisfies the PRD control-plane/tenant-plane rule. Reusing the approval engine avoids a second, divergent approval authority and keeps commercial exceptions auditable in one place.
**Consequences:** FX, statutory tax, GL, PDF invoices, and dunning scheduling remain deferred. Write-off authority depends on either a linked approved commercial-exception instance or the `finance.commercial_terms.approve` permission — the safer configurable behaviour chosen under the AGENTS ambiguity rule and documented here. Verified by unit tests (no-float money helpers, derivation) and smoke tests (overpay 400, governed PATCH 400, append-only history, terms-threshold → engine instance).
